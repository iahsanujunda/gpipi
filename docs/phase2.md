# Household Budget Bot — Phase 2: Frontend & Magic-Link Auth

_Slack-brokered web UI · Stack: React (Cloudflare-hosted static assets) · Ktor (shared backend) · Exposed/Postgres · Flyway · magic-link → HttpOnly session_

---

## System context

The household budget system lets the members of one household track shared spending. In phase 1, users log expenses through a Slack bot (`@ai just paid 1500 for ramen`); a Ktor backend extracts, categorizes, and stores each expense in Postgres (via Exposed, with table classes generated by pgen from Flyway migrations). The Slack workspace is private to the household — only its members are in it — so workspace membership is a trustworthy identity signal.

Phase 2 adds a **React web frontend** for the parts of budget management that don't fit a chat command: reviewing expenses, seeing wallet/account balances derived from recorded activity, allocating payday income, moving money between wallets, editing budget lines, and tracking savings goals.

This introduces a second way to reach the backend. The phase 1 backend authenticates Slack requests by verifying Slack's request signature; that mechanism does not cover a browser client, which needs its own scheme. This document specifies that scheme, the shared architecture, and four independently deployable iterations.

---

## Iteration Order Rationale

Ordering is driven by **what retires the most manual effort soonest**, not by technical foundation. The whole system exists to replace a spreadsheet; each iteration is sequenced toward closing it, and each ships a complete, usable feature on its own.

| # | Scope | Why This Order |
|---|-------|----------------|
| 1 | Auth foundation + expense list | Auth is the spine every screen needs; a read-only expense table is the cheapest way to prove the full magic-link flow end-to-end before any write risk exists |
| 2 | Wallets + payday funding | The critical path — show where recorded money went, then make payday allocation and between-wallet reallocation quick. Establishes the first balance-affecting web write path |
| 3 | Budget management (view + edit) | Already delivers category CRUD and spend-vs-cap; iteration 2 extends each budget line with its required wallet association |
| 4 | Savings goals | Lowest frequency (checked rarely, easy to do manually); reuses iteration 2's wallet balance projection, so it lands almost for free |

You could stop after **iteration 2** and have already retired the spreadsheet — that is the test of whether the ordering is right.

## Reference: Authentication Model (magic link → session)

All four iterations sit behind this. Iteration 1 implements it; 2–4 rely on it.

Identity is brokered by Slack. Because the workspace contains only household members, a request initiated from Slack is already attributable to a known user, so the frontend is authorized off the back of a Slack action rather than a separate login. This is the standard **magic-link** pattern.

### Two tokens (never a credential in the URL)

A credential placed *in a URL* leaks — through browser history, server/proxy access logs, and the `Referer` header sent to any third-party resource the page loads. So the link carries a **single-use nonce**, not the session; the nonce is immediately exchanged for a **session** delivered as an `HttpOnly` cookie that never appears in a URL.

```
User issues a command in Slack (e.g. "@ai open budget")
  → backend mints a random nonce; stores only its SHA-256 HASH:
      { nonce_hash, user_id, expires_at (~10 min), consumed_at=null } → Postgres
  → posts the raw nonce back EPHEMERALLY (chat.postEphemeral, only the issuer sees it):
      https://<frontend>/enter#<nonce>                     (fragment — kept out of logs/Referer)

User clicks
  → frontend reads nonce from location.hash → POST /api/auth/redeem { nonce }
      → backend hashes the presented nonce, then validates + consumes in ONE updateReturning:
          match on nonce_hash WHERE expires_at > now AND consumed_at IS NULL, set consumed_at = now
      → the atomic update returns the user_id iff the row was still redeemable
        (a leaked/double-clicked nonce cannot be reused — the second update matches nothing)
      → set session cookie: HttpOnly; Secure; SameSite=Lax; 8-hour idle window
  ← nonce is dead; the URL in history is worthless

Subsequent /api/** calls → carry the session cookie; endpoints check the SESSION, never the nonce
```

The raw nonce lives only in the link (and briefly in the browser); at rest we keep just its hash, so a Postgres dump can't be replayed into sessions. Delivering the link **ephemerally to the issuer** also closes an identity trap: the nonce is minted for whoever ran `@ai open`, so if another member could see and click it they'd get a session acting *as* the issuer. `chat.postEphemeral` means only the issuer ever sees their own link.

### Three non-negotiables

1. **Nonce is single-use**, enforced transactionally — validation and the `consumed_at` flip in one `updateReturning` inside a `dbQuery` block, so concurrent/repeat redemptions can't both succeed (proven by a concurrent-consumers test).
2. **Session lives in an `HttpOnly` cookie** — never the URL, never `localStorage`. Set `Secure` (HTTPS only) and `SameSite=Lax` as defense in depth; unsafe browser API requests also require an exact trusted `Origin`.
3. **Verify before trust** — `/api/auth/redeem` is the only public route; every other `/api/**` requires a valid session.

### Session lifetime policy

- **Nonce: ~5–10 min** — only needs to survive from link-post to click.
- **Session idle timeout: 8 hours** — each authenticated request renews the cookie's browser-side `Max-Age`.
- **Session absolute lifetime: 24 hours** — the server validates the signed `issuedAt` on every request and requires a new Slack-issued nonce once the full day elapses, regardless of activity.

### Identity carried through

The nonce stores the `user_id` of the member who issued the command, so the session knows which member is acting — supporting per-member views without a separate identity system.

### `auth_nonce` schema

```sql
create table auth_nonce (
    id          uuid        primary key default gen_random_uuid(),
    nonce_hash  text        not null unique,  -- SHA-256 of the raw nonce; the raw is NEVER stored
    user_id     text        not null,         -- the member the link was minted for
    expires_at  timestamptz not null,         -- ~10 minutes out
    consumed_at timestamptz,                   -- null = unconsumed; set on redeem (single-use)
    created_at  timestamptz not null default now()
);
```

> Two deliberate deviations from a naive design: the primary key is a surrogate `id` and the nonce is keyed by a **hashed** column (`nonce_hash unique`), never the raw value — so a DB leak can't be replayed. And `consumed` is a **timestamp** (`consumed_at`), not a boolean, so redemption is observable ("when was this consumed") for free. `AuthNonceRepository.consume` does the validate-and-flip as a single `updateReturning`; `AuthService` owns the hashing (mint hashes before insert, redeem hashes before lookup) so the two sides can never drift.

**Session mechanism (concrete).** A signed **stateless** cookie via Ktor's `Sessions` plugin — no `session` table. The payload is `UserSession(userId, issuedAt)`, signed (not encrypted) with `SessionTransportTransformerMessageAuthentication` keyed on `SESSION_SIGN_KEY`; the cookie is `HttpOnly`, `Secure` (gated on env so local http still works), and `SameSite=Lax`. Its `Max-Age` is renewed to 8 hours on each authenticated request, while the guard rejects the signed payload once `issuedAt` reaches the server-enforced 24-hour absolute lifetime. A fresh `@ai open` flow then mints a new nonce and session. Add a server-side `session` table only if revocation is ever wanted. Expired/consumed nonces are swept by a periodic cleanup job.

## Reference: Two Doors, One Authorization Model

A web UI plus a Slack bot can appear to need two separate auth systems. They don't — there are two **authentication front-doors** that resolve to one authorization model.

```
Slack request      ──▶  Slack signature verification (phase 1)  ──┐
                                                                  ├──▶  validated user_id  ──▶  service logic
Frontend request   ──▶  session-cookie check (phase 2)          ──┘
```

Each door is middleware producing an authenticated `user_id`. Everything behind the doors — expense, budget, account, and money-movement logic — is identical and door-agnostic.

## Reference: A Category *Is* a Budget Line

Phase 1 iteration 3 merged `budget_envelope` into `category`. There is one table of budget lines; each starts with a `name`, `description`, `period`, `amount` (the cap), `active`, and `slack_loggable`. Iteration 2 adds the required `account_id`.

That last flag matters here. Fixed obligations — mortgage, insurance, recurring transfers, investment contributions — are `slack_loggable = false`: nobody types them into Slack, but they still need a wallet association so the budget screen and future recorded activity have one consistent destination. So:

- **Phase 1's extraction** reads `active = true and slack_loggable = true` (only typeable categories in the enum).
- **Phase 2's wallet and budget screens** read **all** `active` categories, loggable or not.

Same table, two projections. Add the second as a distinct repository method with an explicit column list rather than widening the first.

---

## Reference: Balances Follow Recorded Activity, Not the Bank

The system still does **not** mirror a bank balance or require an opening balance. A wallet/account balance is the household system's own running balance:

```
incoming money movements − outgoing money movements − recorded expenses
```

Every budget line has exactly one wallet/account. When an expense is confirmed, that wallet is copied onto the expense and debited immediately. This snapshot matters: changing a budget line's wallet later affects future expenses, not history. If an existing expense is explicitly recategorized, the correction updates both its category and wallet together.

Balances may be negative. That is expected when spending predates the household's first recorded top-up or when the real account had a pre-existing balance that was never entered. A member can add an external top-up later if they want the tracked balance to converge, but the migration does not invent an opening balance.

# Iteration 1 — Auth Foundation + Expense List

Stands up the entire magic-link flow and proves it with one read-only feature. No mutations, so no write-side risk while the auth spine is shaken out. Delivers immediate value: expenses on a real screen instead of Slack scrollback.

### 1.1 Architecture

```
React  /enter#<nonce>
  → POST /api/auth/redeem { nonce }   (public)
      → validate + consume nonce (one dbQuery block) → set HttpOnly session cookie
  → GET /api/expenses                 (session-guarded)
      → list from phase-1 expense table (joined to category)
  → render sortable/filterable data table

Slack (phase-1 bot): "@ai open" / "@ai open budget"
  → OpenBudgetCommand (a SlackCommand in the phase-1 dispatcher, see phase 1 appendix)
  → mint auth_nonce (store hash) → post magic link EPHEMERALLY to the issuer
```

### 1.2 Schema

- `auth_nonce` (see Authentication reference). New.
- No new domain tables — reads phase 1's existing `expense` + `category`.
- First Flyway migration of phase 2: `V{n}__auth_nonce.sql`.
- **Regenerate pgen table classes after the migration** (`pgenGenerateSpec` → `pgenGenerateCode`), and add `auth_nonce` to the pgen `tableFilter` allowlist — new tables are not generated otherwise.

### 1.3 Endpoints

| Method | Path | Guard | Purpose |
|--------|------|-------|---------|
| POST | `/api/auth/redeem` | public | Exchange a nonce for a session cookie |
| GET | `/api/auth/session` | session | Current member for the session cookie, or 401 — the frontend's bootstrap check on load |
| GET | `/api/expenses` | session | Paginated expense list (filter by date range, category) |
| POST | `/api/auth/logout` | session | Clear the session cookie |

`/api/auth/session` is guarded, not public: the frontend calls it on load and treats a 401 as "not signed in" (no session yet), so `/api/auth/redeem` remains the *only* truly public route. Plus a phase-1-side `SlackCommand` (`OpenBudgetCommand`) that mints the nonce and posts the link ephemerally (the frontend's entry point).

### 1.4 Session Guard

A Ktor `Authentication` provider named `"auth-session"` wrapping the `/api/**` group (except `/api/auth/redeem`): it reads the signed session cookie, validates the signature, resolves `user_id` from `UserSession`, and returns 401 if absent/expired/tampered. Protected routes sit inside an `authenticate("auth-session") { … }` block; `configureSecurity()` installs both `Sessions` and `Authentication` before routing. This is the frontend's equivalent of phase 1's per-route Slack signature verification — the second door.

### 1.5 Frontend

- `/enter` route: reads `location.hash`, POSTs redeem, then routes into the app.
- Expense table: columns (date, description from the Slack message with its mention and exact extracted amount removed from either edge, category, amount); client sort + date/category filter; read-only. Other numbers remain intact. An extracted note is accepted only when it is a contiguous span copied from the original Slack message; model-authored analysis is discarded before the draft is stored. That verified user text is the fallback after raw Slack text expires.
- Activity visual baseline: [mobile default mockup](mockups/activity-mobile-default.svg), with cards on phones and the same fields promoted to a table from medium widths upward. Phone selectors and date pickers follow the shared animated bottom-drawer pattern shown in the [drawer-state mockup](mockups/activity-mobile-drawer-states.svg).
- Production exposes the frontend and `/api/**` under one browser origin: Cloudflare serves the static app and reverse-proxies `/api/**` to Ktor. `VITE_API_URL` therefore stays unset in production, just as it does behind Vite's local proxy. This keeps the signed `SameSite=Lax` session cookie first-party; CORS is not relied on to make cross-site cookies work.

### Definition of Done

- [ ] `auth_nonce` table created (Flyway migration) and registered in the pgen `tableFilter`
- [ ] `OpenBudgetCommand` mints a nonce (hash stored) and posts a magic link **ephemerally** (`chat.postEphemeral`) to the requesting member; mint failure sends ephemeral feedback
- [ ] `/api/auth/redeem` hashes + validates + consumes the nonce in one `updateReturning`, sets `HttpOnly; Secure; SameSite=Lax` signed cookie
- [ ] Consumed or expired nonce is rejected (single-use proven by test)
- [ ] `/api/**` rejects requests without a valid session; `/api/auth/redeem` is the only public route (`/api/auth/session` is guarded and returns 401 when unauthenticated)
- [ ] Session carries the acting member's `user_id`
- [ ] Session renews an 8-hour idle cookie on authenticated activity and is rejected after its 24-hour absolute lifetime
- [ ] `GET /api/expenses` returns the phase-1 expenses, filterable by date/category
- [ ] React app deployed on Cloudflare with same-origin `/api/**` proxying to Ktor
- [ ] Nonce cleanup runs on a schedule
- [ ] End-to-end: Slack command → click link → expense table renders

# Iteration 2 — Wallets & Payday Funding

The critical path. This is what lets the spreadsheet close: every recorded expense visibly reduces the wallet that funded its budget line, and payday becomes a fast sequence of explicit money movements rather than a generated monthly plan.

The product calls these records **wallets** in navigation and headings. The schema and API use **account** because a record may represent a real bank account, a settlement account, cash, or a deliberately virtual envelope. Both names refer to the same object.

### 2.1 Domain Model

Three primitives:

- **`account`** — a tracked wallet/account with an editable name and optional description. It starts at a derived balance of ¥0; there is no opening-balance field.
- **`category.account_id`** — the required wallet association for a budget line. Many budget lines may point to the same account.
- **`money_movement`** — an append-only record of money entering, leaving, or moving between tracked accounts.

Every confirmed expense also stores **`expense.account_id`**. It is copied from the selected category at confirmation time, so the expense immediately affects that account and remains attached to it even if the category is routed elsewhere later.

The displayed balance is always derived, never stored:

```
account balance
  = sum(movements into account)
  − sum(movements out of account)
  − sum(expenses recorded against account)
```

Movement shapes:

- `from_account_id = null`, tracked `to_account_id` → external top-up, such as salary, side-gig income, or cash.
- tracked `from_account_id`, `to_account_id = null` → money sent outside the tracked system.
- both tracked → reallocation; debit the source and credit the destination atomically.
- both null, or the same tracked account on both sides → invalid.

“External account” is a selector option, not a row in `account`; the optional note carries details such as `July salary · employer`. This keeps employers and one-off sources out of the wallet list.

### 2.2 Schema and Migration

At the current repository head, this is Flyway migration `V13__wallet_accounts.sql`. It intentionally alters the phase-1 `category` and `expense` tables:

```sql
create table account (
    id          uuid primary key default gen_random_uuid(),
    name        text        not null unique,
    description text,
    created_at  timestamptz not null default now(),
    updated_at  timestamptz not null default now()
);

alter table category
    add column account_id uuid references account(id);

-- Safe upgrade path for all existing installations.
insert into account (name, description)
values ('Default wallet', 'Created automatically for existing budget lines');

update category
set account_id = (select id from account where name = 'Default wallet')
where account_id is null;

alter table category
    alter column account_id set not null;

alter table expense
    add column account_id uuid references account(id);

-- Historical expenses follow their budget line's migration assignment.
update expense e
set account_id = c.account_id
from category c
where e.category_id = c.id
  and e.account_id is null;

alter table expense
    alter column account_id set not null;

create table money_movement (
    id                 uuid primary key default gen_random_uuid(),
    idempotency_key    uuid        not null unique,
    from_account_id    uuid references account(id),
    to_account_id      uuid references account(id),
    amount             bigint      not null check (amount > 0),
    occurred_at        timestamptz not null,
    note               text,
    created_by_user_id text       not null,
    created_at         timestamptz not null default now(),
    check (from_account_id is not null or to_account_id is not null),
    check (
        from_account_id is null
        or to_account_id is null
        or from_account_id <> to_account_id
    )
);

create index category_account_id_idx on category (account_id);
create index expense_account_spent_at_idx
    on expense (account_id, spent_at desc, id desc);
create index money_movement_from_occurred_at_idx
    on money_movement (from_account_id, occurred_at desc, id desc);
create index money_movement_to_occurred_at_idx
    on money_movement (to_account_id, occurred_at desc, id desc);
```

The migration creates exactly one ordinary account named **Default wallet**, assigns it to **every existing budget line** (active and inactive), then snapshots that assignment onto every historical expense. The account is not protected or magic after migration: members can rename or edit it later, and the foreign keys remain intact. New budget lines must provide an `account_id`; there is no nullable post-migration state.

Immediately after migration, `Default wallet` will usually be negative because it contains historical expenses but no invented incoming movement. That is the truthful initial state and must not be “fixed” by seeding fake funding.

The migration and service must be tested with existing categories and expenses, not only against an empty database. Add `account` and `money_movement` to the pgen `tableFilter` allowlist, regenerate (`pgenGenerateSpec` → `pgenGenerateCode`), and commit the updated spec.

### 2.3 Expense Attribution

The Slack confirmation path changes:

1. Resolve the final `category_id`.
2. Read that category's required `account_id`.
3. Insert the expense with both IDs in the same database transaction.
4. Return/announce the recorded category as before.

`ExpenseRepository.insert` remains the single expense-write boundary and is extended to resolve/snapshot the account from `category_id`; `SlackInteractionHandler.handleConfirm` must not accept or trust a separately supplied account ID. Both existing insert overloads converge on that invariant so no recording path can omit wallet attribution.

Do not derive historical wallet attribution by joining through the category at read time. That would silently move old spending whenever a budget line changes wallets. An explicit expense recategorization is different: it updates `category_id` and snapshots the new category's current `account_id` atomically, intentionally moving that expense between wallet projections.

### 2.4 Money Movement

Payday is a repeated use of the same movement form:

- Choose **External account** as From.
- Choose the tracked wallet/account as To.
- Enter the amount and optional note.
- Review and record the movement.

Reallocation uses the same form with a tracked account on both sides. Sending money out uses a tracked source and **External account** as the destination. A tracked-to-tracked movement is one database row and one transaction; never create two loosely coupled rows.

When the drawer is opened from a wallet card, that wallet is pre-filled as **To** and **External account** is the default **From** — the payday top-up is the highest-frequency action, so it is the zero-configuration path. A centered icon-only **Swap** button with up/down opposed arrows sits between the vertically stacked From and To selectors and exchanges the two endpoints in place, so the same card-launched drawer reaches an external send (tracked wallet moved into From) or a reallocation (a second tracked wallet chosen on the other side) without re-selecting the wallet the user started from. Its accessible name is `Swap From and To`; Swap preserves amount, date, and note, then requests a fresh preview.

Money movements are append-only in this iteration. If correction becomes necessary, add a reversing movement rather than mutating history. Account metadata and a budget line's future wallet association remain editable. Accounts are not deletable or deactivatable in this iteration because budgets, historical expenses, and movements reference them.

### 2.5 Reads and Endpoints

| Method | Path | Guard | Purpose |
|--------|------|-------|---------|
| GET | `/api/accounts` | session | Accounts with derived balance and assigned-budget count |
| POST | `/api/accounts` | session | Create an account; starts at a derived ¥0 |
| GET | `/api/accounts/{id}` | session | Account metadata, balance, and assigned budgets |
| PUT | `/api/accounts/{id}` | session | Edit account name/description |
| GET | `/api/accounts/{id}/transactions` | session | Paginated merged timeline of expenses and money movements for this account |
| POST | `/api/money-movements/preview` | session | Validate a proposed movement and return affected balances before/after without writing |
| POST | `/api/money-movements` | session | Record an external top-up/send or tracked-account reallocation |

The reusable movement input is `{ fromAccountId?, toAccountId?, amount, occurredOn, note? }`; a missing endpoint means `External account`, and `occurredOn` is an ISO local date (`YYYY-MM-DD`) in `Asia/Tokyo`. The preview accepts that input directly. The write adds a client-generated key: `{ idempotencyKey, ...movementInput }`.

The server takes `createdByUserId` from the authenticated principal, never from the request, and validates the endpoint, amount, and occurrence-date rules through a single shared routine (`MoneyMovementService.validate`) before entering the repository. `occurredOn` must be on or before `LocalDate.now(clock.withZone(DEFAULT_BUDGET_ZONE))`; the frontend sets the date control's maximum to that same household-local today, but the backend remains authoritative and rejects future dates. On write, the service converts today to the server's current instant and a past date to the start of that day in `Asia/Tokyo`, then persists the resulting `occurred_at`. Both `/preview` and the write run the shared validation routine, so the two paths cannot drift into “preview says valid, write rejects” for domain validation.

The preview endpoint returns `{ calculatedAt, accounts: [{ accountId, name, balanceBefore, delta, balanceAfter }] }` for tracked accounts only. It owns the balance formula and is authoritative **as of `calculatedAt`**, but it is not a reservation: another household expense or movement may be recorded before confirmation. Because a balance is a running total (`sum incoming − outgoing − expenses`) and not an as-of-date figure, `occurredOn` never changes the previewed `balanceAfter` — it only affects where the movement lands in a wallet's transaction timeline. The preview must not be implemented as a point-in-time balance.

`POST /api/money-movements` revalidates and inserts the movement in one database transaction, recomputes the affected account projections after the insert, and returns those authoritative post-write balances with the created movement. The frontend replaces the preview with that response and invalidates account-list and detail queries. Negative projected or final balances remain valid and never block confirmation.

`idempotencyKey` is generated once when a valid movement advances to Review and is retained through confirmation and every network retry. It is replaced only after a confirmed success or when the user leaves that review and starts a different submission. The database uniqueness constraint is the final guard against double-taps and ambiguous-response retries. Reusing a key with the same authenticated user and identical movement input returns the originally created movement without another insert (`201 Created` for the first write, `200 OK` for a replay); reusing it with different input or a different user returns `409 Conflict`. The replay response recomputes current affected balances so its response remains authoritative when it is returned.

The repository implements this without a check-then-insert race: `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING`, then select the row by key in the same transaction. The service compares the authenticated user and canonical validated input with the selected row before treating it as a replay. A conflicting payload is not silently accepted, and concurrent requests with the same key can commit at most one movement.

`GET /api/accounts/{id}/transactions` is a read projection, not a new ledger table:

- Query parameters are `limit` (default `50`, maximum `100`) and an optional opaque `cursor`.
- The response is `{ items, nextCursor? }`. Each item is a discriminated union:
  - Expense: `{ kind: "EXPENSE", id, occurredAt, signedAmount, merchant?, description?, categoryName, note? }`.
  - Movement: `{ kind: "MONEY_MOVEMENT", id, occurredAt, signedAmount, direction, counterpartyAccountId?, counterpartyName, note? }`, where `direction` is `INCOMING` or `OUTGOING` and an external endpoint uses `counterpartyName: "External account"`.
- Expenses always have a negative `signedAmount`. Movements are signed from the requested account's perspective: incoming positive, outgoing negative.
- The repository uses a `UNION ALL` read projection ordered newest-first by `(occurred_at, kind_rank, id)` descending. `kind_rank` is fixed (`EXPENSE = 0`, `MONEY_MOVEMENT = 1`). The opaque cursor encodes that complete tuple, and the next page uses a strict keyset comparison; offset pagination is not used.
- `nextCursor` is omitted when no later item exists. Invalid cursors or limits return `400`; an unknown account returns `404`.

There is deliberately no global transfer ledger, monthly payday plan, variance endpoint, funder model, or mutable balance column.

### 2.6 Frontend

- `/wallets` is the primary wallet view: cards show account name, assigned-budget count, and current derived balance. Negative balances are rendered normally, not as data errors.
- `Add wallet or account` is the Wallets page action in the shared launcher. New accounts start at ¥0.
- Tapping a card opens its detail view; a trailing right chevron makes this navigation affordance visible alongside the separate `Move money` action. The account title has an adjacent Edit action; the rest of the page shows assigned budgets, current balance, and that account's transactions.
- The detail timeline reuses Activity's mobile transaction-card hierarchy: description/source and signed amount, category or movement chip, then date/note metadata.
- Each wallet card exposes `Move money`. The adaptive movement drawer supports external top-up, external send, and tracked-to-tracked reallocation, opening pre-filled per §2.4 with a labelled `Swap From and To` action.
- Once endpoints, amount, and occurrence date are valid, the drawer requests the backend preview and shows its `balanceBefore → balanceAfter` values. External top-up/send shows the single tracked wallet; reallocation shows both. **External account** has no tracked balance and is deliberately absent.
- Preview requests are **debounced** on input and applied **latest-wins**: each request is tagged, and a response is rendered only if it matches the current input, so an earlier (slower) preview can never overwrite the value for the amount now on screen.
- Preview failures degrade without trapping the user. Invalid input (same account on both sides, amount ≤ 0, or a future occurrence date) shows the validation message inline and disables `Review money movement`. A failed or slow preview *network* call hides the before/after panel but still allows Review because `POST /api/money-movements` revalidates and returns authoritative balances at write time. Preview loading keeps the fields editable and shows a stable skeleton; an error preserves input, explains that balances could not be refreshed, and offers Retry.
- The Review surface shows projected balances when the current preview succeeded. If it did not, Review instead shows `Balance preview unavailable — final balances will be checked when you record this movement`; confirmation remains available. The drawer replaces either state with the write response and invalidates the account-list and detail queries.
- The preview is labelled as current recorded state, not guaranteed future state. Confirmation always uses the post-write balances returned by `POST /api/money-movements`.
- There is no standalone ledger view. Users inspect activity in the context of the wallet whose balance it affected.
- The interaction baseline is [wallets and money movement](mockups/payday-funding-views.svg).
- Production uses same-origin `/api/**` proxying, a host-only `Secure; HttpOnly; SameSite=Lax` session cookie, and exact Origin validation on every unsafe browser API request (`POST`, `PUT`, `PATCH`, and `DELETE`, including `/api/auth/redeem`). Ktor compares `Origin` with the configured `web.baseUrl`; a missing or different origin receives `403` before route logic runs. CORS is transport configuration, not CSRF protection.

# Iteration 3 — Budget Management (View + Edit)

Manages budget-line definitions and spend-vs-cap history. The category-only slice shipped before wallets; iteration 2 extends the same editor and read models with the required account association shown in the approved budget mockups.

### 3.1 Scope

- View/edit/create the phase-1 `category` table as budget lines: `name`, `description`, `period`, `amount`, `active`, `slack_loggable`, and required `account_id`.
- Spend-vs-cap view: expenses-in-period against each line's `amount`.
- Each budget line names one wallet/account; many lines may share one account. The account selector is required for create and edit.
- The migration's `Default wallet` keeps existing records valid. New forms may preselect the only available account, but must show the selection explicitly in the review step.

Editing `description` here directly tunes phase-1 categorization (it is the LLM disambiguation hint), and toggling `slack_loggable` adds or removes a line from the extraction enum. Active extraction categories use a generation-keyed five-minute cache: every successful category mutation advances the generation after commit and eagerly rebuilds it. Concurrent readers share one rebuild, and a reader retries rather than returning a generation superseded while it was loading. A failed eager rebuild does not turn a committed mutation into an apparent API failure; the next extraction retries the current generation.

**Layering.** Mirrors the `AuthService`/`AuthRoutes` split from iteration 1: `BudgetService` owns validation and orchestration and returns a sealed `BudgetMutationResult` (`Created` / `Updated` / `NotFound` / `Invalid` / `DuplicateName`); `budgetApiRoutes` only maps that result to an HTTP status — no business logic in the route layer. `CategoryRepository` does plain persistence (`create`/`update`/`deactivate`/`listBudgets`, the last returning **all** active categories regardless of `slack_loggable`, unlike `findActive()`). A duplicate `name` surfaces as an `ExposedSQLException` from the DB's unique constraint, caught in `BudgetService` and mapped to `DuplicateName` → 409 — there's no separate application-level uniqueness check.

**Deactivate is a dedicated endpoint, not a PUT flag.** `PUT /categories/{id}` is a full replace (every field required), so folding `active: false` into it would mean deactivating requires resending the entire line correctly — and would let a routine edit accidentally *reactivate* a line if the client's edit form ever forgot to carry `active` forward. `PUT /categories/{id}/deactivate` removes that footgun entirely: the frontend's edit form doesn't expose `active` as an editable field at all, and deactivation only happens through its own confirmation flow.

### 3.2 Endpoints

| Method | Path | Guard | Purpose |
|--------|------|-------|---------|
| GET | `/api/budgets` | session | All active categories, including `accountId` and account name |
| POST | `/api/budgets/categories` | session | Create a budget line with required `accountId` |
| PUT | `/api/budgets/categories/{id}` | session | Full-replace edit: name/description/period/amount/slack_loggable/accountId |
| PUT | `/api/budgets/categories/{id}/deactivate` | session | Deactivate only — the sole way `active` is ever set to `false` |
| GET | `/api/budgets/spend?date=` | session | Spend vs. cap per line for the bucket containing `date` (defaults to today's date in Tokyo) |

**Spend-vs-cap bucketing (`3.2a`).** A category's `period` is its own — WEEKLY or MONTHLY — so a single `?period=YYYY-MM` param (the original spec) can't cleanly cover weekly lines: comparing a weekly ¥3,000 cap against a full month's spend would always read as over budget. Instead, `?date=YYYY-MM-DD` (default today's date in Tokyo) is bucketed **per category**, using that category's own period: `BudgetPeriod.bucketFor(date, zone)` resolves a MONTHLY line to the calendar month containing `date`, and a WEEKLY line to the ISO week (Monday–Sunday) containing it. Each spend row returns `windowStart` and the half-open `windowEndExclusive` as local ISO dates so the frontend displays the same authoritative window used by the calculation. Both layers use the shared `DEFAULT_BUDGET_ZONE` (`Asia/Tokyo`): `budgetApiRoutes` converts its injectable clock to that zone before resolving an omitted date, and `BudgetService` uses it for bucket boundaries. This makes the household's actual "today" explicit instead of inheriting the server's local zone or UTC. At household scale (a handful of budget lines), `BudgetService.spendVsCap` computes this as one small per-category loop (`listBudgets()` then `ExpenseRepository.sumAmount(categoryId, from, to)` per row) rather than one clever aggregate query — consistent with this project's general preference for deterministic, simple queries (see phase 1's iteration-8 stance on deterministic SQL over agent loops).

The frontend maintains **independent weekly and monthly query anchors**. Moving to a previous ISO week never changes the selected calendar month, and moving to a previous month never changes the selected week. Future navigation is disabled and each historical section offers a direct return to its current period. A week that crosses a month boundary renders both endpoint months on one line (`29 JUN – 5 JUL`) in a selectively wider period control rather than wrapping the ending month. Category configuration is not versioned yet, so historical spending is explicitly labelled against the line's **current cap**; it must not be presented as the cap that was necessarily in force during that past period.

### 3.3 Frontend

- Budget editor: create/edit as a bottom-sheet (mobile) or dialog (desktop) form — `BudgetEditor.jsx`. Wallet/account is a required selector in the same form.
- The edit form's initial state is loaded directly from the already-fetched `BudgetRow` (`formFromBudget(budget)`), never a blank/defaulted object — this is what keeps a routine edit from silently touching `active`/`slack_loggable` fields the user didn't intend to change.
- Budget cards and desktop rows display the associated account by name. The review step includes it for create and shows previous → next when an edit changes it.
- Changing a budget line's account affects future expenses only; historical expense balances remain against their snapshotted `expense.account_id`.
- Budget lines are grouped into Weekly and Monthly sections, each with its own previous/next cursor and current-period reset. Mobile keeps 44px navigation targets; medium-and-up layouts render one table per cadence rather than one mixed-period table.
- Historical rows retain the same exact spend and utilization presentation, but use `under/over current cap` language rather than `left/over` so the UI does not imply that mutable category caps are historical snapshots.
- Edits use a confirm step showing **only the changed fields** (previous → next) before commit; create shows a full summary. A mis-set cap is higher-stakes than a mis-categorized expense.
- Deactivate rather than delete: expenses reference `category_id` by FK, so removal breaks history. Deactivating has its own confirmation screen, separate from the edit-changes review, and calls the dedicated `/deactivate` endpoint.
- Unsaved-edit protection: an in-app navigation guard plus a `beforeunload` handler warn before losing dirty form state.
- Spend-vs-cap renders as a secondary layer on the existing budget cards/table (joined by `categoryId`), not a blocking dependency — the page still renders caps if the spend query fails or is slow.

### 3.4 Cross-door note

Chat-driven budget edits (e.g. `@ai set the weekend-eat budget to 40000`) are the **same mutation over the same data**, through the Slack door instead of the web door — they belong to phase 1's bot/intent surface (iteration 8) as a new `SlackCommand` in the dispatcher (see phase 1 appendix), not here. Both doors resolve to the same authorized write; this iteration is the web door for it.

# Iteration 4 — Savings Goals

The lowest-frequency feature (savings are checked rarely and are easy to do manually), so it's the capstone. It reuses iteration 2's `account` and balance projection rather than introducing a parallel savings container — a savings wallet is just an account with an optional goal.

### 4.1 Model

- A **goal** is an optional target on an account (`goal_amount`).
- **Balance** is the same iteration-2 projection used everywhere: movements in minus movements out minus expenses attributed to the account.
- **"X to go"** = `goal_amount` − derived balance.

Because surplus sweeps and other movements are recorded in iteration 2, they already show up here. Spending assigned to the same account reduces goal progress as well; no separate savings balance is stored.

### 4.2 Schema

```sql
alter table account add column goal_amount bigint;   -- nullable; set only on accounts with a savings goal
```

(A separate `savings_goal` table is unnecessary at this scope — a nullable column on `account` suffices. Revisit only if an account ever needs multiple goals.)

### 4.3 Endpoints

| Method | Path | Guard | Purpose |
|--------|------|-------|---------|
| PUT | `/api/accounts/{id}/goal` | session | Set or clear a goal amount |
| GET | `/api/accounts` | session | Existing account list projection extended with goal progress and "X to go" |

### 4.4 Cross-door note

A chat query (e.g. `@ai how much in the travel account`) is the same derived-balance read through the Slack door — an intent for phase 1's iteration-8 query path. This iteration is the web view of the same computation.

### 4.5 Frontend

- Savings view: accounts that have goals, each with a progress bar (balance / goal) and "X to go".
- Optional: accounts without goals shown as plain derived balances.

## Cross-Cutting

- **Migrations + codegen:** each iteration adds a Flyway SQL migration (source of truth), registers any new table in the pgen `tableFilter` allowlist, then regenerates (`pgenGenerateSpec` → `pgenGenerateCode`) and commits `pgen-spec.json`. Forgetting the allowlist step means the table silently isn't generated.
- **Persistence discipline:** all DB access through `dbQuery(db)`; one flat transaction per atomic write; no network calls inside a transaction. Generated tables are plain Exposed `Table`s (not `IdTable`), so ids are generated client-side (`UUID.randomUUID()`) and set explicitly — there is no `insertAndGetId`.
- **Testing:** Testcontainers + real migrations, as in phase 1. The iteration-2 migration needs both fresh-install coverage and an upgrade fixture containing pre-existing categories and expenses. Money-movement tests include concurrent same-key submission, mismatched-key replay, the Tokyo today/future boundary, and equal-time transaction pagination. `cleanDatabase()` truncates seed data, so tests needing FK targets must create accounts/categories in setup.
- **Browser deployment + CSRF:** production exposes Cloudflare-hosted assets and Ktor's `/api/**` under one browser origin, with Cloudflare proxying the API path. This keeps the session cookie first-party. Ktor also rejects every unsafe browser API request whose `Origin` is absent or differs from `web.baseUrl`; CORS never substitutes for this check.
- **Config keys (added in iter 1):** `session.signKey` ← `SESSION_SIGN_KEY` (HMAC key for the session cookie), `web.baseUrl` ← `WEB_BASE_URL` (the full canonical browser origin, used for magic links and exact Origin validation), `cors.allowedOrigin` ← `CORS_ALLOWED_ORIGIN` (host[:port], no scheme — retained for explicitly configured local/test cross-origin access only). All three are read with `config.property(...)`, which throws on boot if missing; mirror them in `.env.example` and inject them in the test config (`configureWithTestDb`).
- **Balance projection purity:** balances are always derived from append-only money movements and attributed expenses — never stored as a mutable column.
